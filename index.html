Case Study - 01

Habbit
Tracker

A habit tracking app that doesn't tell you what habits to track or how often - giving users total ownership over their routines for the first time.

Platform
iOS 16+ · SwiftUI
Architecture
MVVM · RESTful APIs · RealmSwift
Key Challenge
Flexible schema vs performance
The Problem
Every habit app assumes it knows you
Streaks for daily push-ups. Weekly meditation. Rigid presets. Real users have custom rhythms - run MWF, meditate weekends, journal when inspired. When the app doesn't bend, users stop using it. Existing solutions have a drop-off rate exceeding 70% after day 14.
Discovery
Three configurations decide success
Through personal use and pattern analysis, I found three variables determine habit adherence: schedule flexibility (not just daily), metric type (count, duration, boolean, numeric), and contextual reminders (not fixed-time alerts). Most apps only solve one.
Build
Reactive schema that flexes with users
Core Data entity model: HabitEntity (name, iconKey, colorHex), ScheduleRule (weekdays bitmask, interval, startDate), CompletionLog (date, metricValue). Combine binds the ViewModel to the SwiftUI view layer with zero boilerplate. UNNotificationCenter schedules per-rule reminders offline - no backend needed.
Decision Layer
Why offline-first over Firebase
Firebase would require an account, a network round-trip for every log, and raised privacy concerns for personal routine data. Core Data runs entirely on-device - under 2ms query time for habit history, zero cold-start latency, and no monthly cost. iCloud sync is a future enhancement via NSPersistentCloudKitContainer.
Impact
Zero friction, any routine
Users can configure any habit - 3x weekly, every 4 days, weekends only - with any metric and smart contextual reminders. The app adapts to the user's life instead of forcing the user to adapt to the app. No server. No account. No excuses.
Case Study - 02

Daily
Expense

An expense tracker that treats every transaction as evidence - with proactive budget alerts, receipt attachments, and a roadmap to auto-import from bank statements via OCR.

Platform
iOS 15+ · SwiftUI / Swift
Data Layer
RealmSwift · RESTful APIs
Key Challenge
Receipt image storage strategy
The Problem
Logs without accountability
Manual expense apps are retrospective by nature - you record what you already spent and learn nothing until it's too late. No receipt evidence means disputed claims during audits. No recurring reminders means missed subscription renewals. No proactive alerts means budget overrun discovered at month-end.
Discovery
Five user needs mapped to features
1) Income logging with source tags (salary, freelance, rental). 2) Expense entries with multi-image receipt proof. 3) Recurring payment reminders (subscriptions, EMIs, rent). 4) Budget threshold alerts at 80% and 90% spend. 5) Future: auto-import transactions via Vision OCR parsing of uploaded bank statements.
Build
Core Data with External Binary Storage
TransactionEntity stores amount, category, date, and notes. Receipt images use Core Data's External Binary Storage attribute - keeping the SQLite file under 10MB while images are managed on disk automatically. UNNotificationCenter schedules recurring reminders per transaction. Budget engine runs threshold evaluation on every new entry.
Decision Layer
Why not store images as BLOB in SQLite
Storing images inline causes Core Data to load every row's binary data during fetch - dramatically slowing list queries as the database grows. External Binary Storage offloads files to the file system, keeping DB reads under 5ms even at 1000+ transactions, while Core Data still manages the lifecycle and cleanup automatically.
Impact
Never miss a bill. Never lose a receipt.
Users receive proactive alerts before exceeding budgets, get reminded of every recurring payment before it hits, and have a timestamped image trail for every expense. The Vision OCR pipeline is architected and ready - bank statement auto-import will drop manual data entry to near zero.
Case Study - 03

Stranger
Chat

A social discovery app where your social currency is earned through real physical activity - making bot-spam structurally impossible and turning fitness into a social habit.

Platform
iOS 15+ · Swift
Protocols
WebRTC · XMPP · HealthKit
Key Challenge
Anti-cheat step verification
The Problem
Frictionless = worthless
Every anonymous chat app faces the same failure: bots, abuse, and dead conversations because there is no cost to participate. Existing platforms respond with human moderation - expensive, slow, and imperfect. The fundamental issue is that interactions carry no weight.
Discovery
Physical effort as social capital
The insight: make social interactions cost something real that a bot cannot fake - physical movement. Steps, distance, and calories burned are verified via HealthKit and converted into an in-app coin balance. Text conversations, audio/video calls, and friend requests each deduct coins. Earn more by moving more.
Build
Four integrated systems
HealthKit telemetry - reads HKQuantityType.stepCount and HKWorkoutActivityType with cadence validation. Core Location geo-hash - converts GPS to geohash for proximity search without exposing exact coordinates. WebRTC peer-to-peer - audio and video call channels with STUN/TURN server configuration. XMPP with Core Data - text messaging with offline queue, read receipts, and thread management.
Decision Layer
Preventing step spoofing
A naive implementation trusts the HealthKit step count - easily gamed by shaking the phone. The solution: step cadence validation using CMPedometer alongside HKWorkoutSession - cross-referencing step frequency, accelerometer rhythm, and session duration. Implausible step rates (>5 steps/second sustained) are flagged and zeroed. Geo-hash radius is obfuscated to prevent exact location triangulation.
Impact
Movement powers connection
The app creates a natural feedback loop: active users earn more coins, can make more connections, which motivates more movement. Bot accounts cannot accumulate coins without genuine physical activity. The ecosystem is self-reinforcing - real users attract real users, spam costs too much to be worth it.
